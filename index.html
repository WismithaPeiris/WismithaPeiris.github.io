Autonomous Vehicle PlatformVision, LiDAR & Real-Time Web Dashboard

End-to-end software platform for a 4-wheel autonomous car on Raspberry Pi 5. Combines dual IMX500 AI cameras, TF Luna LiDAR for distance-based braking, MG996 servo steering, and L298N motor control with a modular Python architecture and real-time web dashboard.

What This Project Does

I wanted to build a small car that could drive itself around a track without any human input. So I put together a Raspberry Pi 5 as the brain, mounted two Sony IMX500 AI cameras on it (one looking forward for lane detection and obstacle spotting, one looking down for a bird's-eye perspective that helps with smooth steering), added a TF Luna laser distance sensor for measuring how far away things are, and wired up a servo motor for steering and a DC motor for driving.

The software side is where most of the work went. I wrote a modular Python codebase with separate modules for perception (processing what the cameras and LiDAR see), planning (deciding what to do next using an 8-state finite state machine), and control (actually turning the wheels using a PID controller that I tuned by hand). The car can follow lanes, detect obstacles, change lanes to go around them, slow down behind a slower object, and emergency-brake if something appears too close. There is also a full web dashboard built with Flask and Socket.IO where I can watch both camera feeds live, see telemetry data, tune the lane detection parameters in real time, and hit an emergency stop button if needed.

I also built a simulator mode so I could test the state machine and control logic on my laptop without needing the physical car, which saved a lot of development time. The entire codebase is written in Python and organized into clean modules that I could work on independently.

Children Interaction RobotFrom API Voice Pipelines to a Push to Talk Platform on Rented H100 and H200 GPU Servers

The complete conversational brain of Figmentum's educational robot for children. It began with API driven voice pipelines and interactive learning games, then evolved into a push to talk platform where a Raspberry Pi 5 streams the child's voice to H100 and H200 GPU servers rented from JarvisLabs.ai, running carefully researched speech to text, language and text to speech models, engineered end to end for ultra low latency.

What This Project Does

I am the prototype engineer behind the conversational side of Figmentum's educational robot for children, and this project tells the full story of how it was built. The first version ran on cloud APIs: the child says the wake word, the robot listens, sends the speech to OpenAI for transcription, thinks with GPT, and answers through ElevenLabs voices with matching emotions. Around that pipeline I built the learning games on a Windows laptop using API models such as GPT and Gemini, which let me prove very early that both the audio path and the camera OCR path worked: a math game where the robot projects a problem and reads the child's written answer through the OAK D camera, a spelling game with spoken and written modes, quizzes, and pronunciation scoring.

Testing with real children exposed the weakness of that design. The wake word pipeline depends on voice activity detection to guess when the child has finished speaking, and children pause, think and restart in ways no silence threshold can predict. Sometimes the robot waited an extra 2 to 5 seconds before answering, and for a young child that delay breaks the magic completely.

So I designed and built the PTT platform, a push to talk system that removes the guessing entirely: the child holds a button to talk and releases it to send. The Raspberry Pi 5 became a thin user end device carrying only the button, the microphone and the speaker, while all the heavy models moved to H100 and H200 GPU servers rented from JarvisLabs.ai, choosing the regions closest to us so network latency stays as low as possible. Each robot keeps one warm encrypted WebSocket open to the server. While the button is held, audio streams up in real time; the moment it is released, the server runs speech to text, a streaming language model and text to speech back to back on localhost, and streams the transcript, the answer text and the spoken voice straight back. The robot starts speaking as soon as the first audio chunk arrives, and the one number the entire system is tuned around is button release to first sound.

The platform is also a research instrument. I studied the open models best suited to children, selected the strongest ones for accuracy and latency, and wired every one of them into the server, so the dashboard can swap the model at each stage per turn and compare combinations: Parakeet TDT, the Canary family, Kid Whisper and Kyutai for speech to text; Qwen3 VL, Llama 3.1, GPT OSS 20B, Phi 4 Mini and Mistral NeMo for the language model; Chatterbox Turbo, Kokoro, Maya1, Dia, Orpheus and Piper for the voice. Because everything runs on the rented servers instead of public APIs, the children's voice data is never sent to any third party, a child specific system prompt shapes every answer, and an optional guard model checks each clause before it is spoken. The result is a repeatable way to find the fastest, most accurate and safest model combination for the final robot.

STT Accuracy Test Bench & Validation PlatformGround Truth Validation of Speech to Text Models for Children

The STT tab of the test bench validation platform I built for Figmentum: a single port web app with a FastAPI backend and a React frontend created to prove which models are good enough for the robot. It runs cloud transcription APIs and open models served on an H100 GPU rented from JarvisLabs.ai through seven strict ground truth validation sections and produces professional PDF reports with clear pass or fail verdicts.

What This Project Does

The robot lives or dies on how well it understands children, and children are the hardest audience in speech recognition: small voices, invented words, long thinking pauses, noisy rooms. Guessing which model handles all of that best was not acceptable, so I implemented the STT tab of Figmentum’s test bench validation platform, a web app with a FastAPI backend and a React frontend served on a single port, to prove it with measurements instead. The vision side of the same platform is project 04.

A run starts with recordings of children's speech and a matching ground truth file. I pick a model and the platform pushes every clip through seven validation sections: transcription accuracy measured by word error rate, pause and disfluency detection, accuracy under background noise, end of turn detection, STT latency, spelling precision measured by character error rate, and projected running cost. The first four are marked as ship blockers because the robot cannot ship if they fail; the rest are important. Every verdict is judged against the ground truth with thresholds I define, never hardcoded limits, so a pass actually means something.

The model list mixes cloud transcription APIs such as GPT 4o Transcribe with the open models served from the STT server I built and deployed on an H100 GPU rented from JarvisLabs.ai, reached through an SSH tunnel: Parakeet TDT v2 and v3, Canary Qwen 2.5B, Canary 1B Flash and v2, Kid Whisper (a Whisper fine tuned on children's speech), Kyutai, and Whisper large v3 turbo in separate lowest latency and highest accuracy variants. Underneath, the scoring engine aligns every transcript word by word and normalizes numbers, spelling, possessives and contractions, handles fillers and disfluencies, and runs homophone and phonetic analysis, so no model is punished for a fair transcription.

Each run ends in a professional PDF report with an executive summary, KPI cards, a validation readiness checklist that separates ship blockers from important checks, and per file detail tables, plus HTML and one page summary formats. State is scoped per browser session so ground truth, audio and results never mix, every run is kept in history, and an automated test suite guards the platform itself. The models that pass here are the ones trusted inside the robot's push to talk system.

OCR Simulation & Benchmarking PlatformHandwriting OCR Test Bench with GPU Served Models and a Pi Capture Station

A two part system for finding the best handwriting OCR for children. A Raspberry Pi capture station photographs handwriting sheets under identical, repeatable conditions, and a vision test bench runs those images through more than 25 OCR models, from cloud APIs to open models served on an H100 class GPU rented from JarvisLabs.ai, with honest accuracy scoring and per stage latency measurement.

What This Project Does

Children write words anywhere on the page, at any angle, in handwriting that is barely formed, and the robot has to read it correctly. Choosing the right OCR model for that job needed two things that did not exist yet: a dataset captured under perfectly consistent conditions, and a bench that measures every model with complete honesty. So I built both.

The Pi capture station is a Raspberry Pi with a Camera Module 3 mounted on a fixed rig at a fixed height and tilt, controlled from a browser dashboard. I engineered the live preview to show the camera's full sensor view exactly as the still will be captured, with no hidden cropping, so what you see is precisely what you get. Autofocus confirmation, a stability check and a sharpness gate make sure a blurred still is never saved, and every image lands as a lossless full resolution file. Because the rig never changes, every photo of children's handwriting in the dataset is directly comparable to every other.

The vision test bench is a web platform with a FastAPI backend and a React frontend running on my laptop, while the models themselves run on an H100 class GPU server rented from JarvisLabs.ai, which the app reaches through a secure tunnel and a small router which spreads requests across two model server instances. Every image passes through a three stage pipeline: page geometry first (upright rotation, keystone correction and page orientation), then PaddleOCR detects each handwritten word on the GPU, crops it upright and classifies whether the crop is right side up, and finally the model under test reads each crop. Whatever a model outputs is stored exactly as recognized, with no silent corrections, because honest numbers were the whole point of building this.

The bench covers more than 25 models: open models served on the GPU such as Nemotron OCR, Nemotron Nano VL, Ministral 3, Molmo2, TrOCR, HTRflow, Llama 3.2 Vision, Phi 3.5 Vision, PaddleOCR VL and Baidu Unlimited OCR, next to cloud APIs like the GPT 4o and 4.1 families, the o series reasoning models, Gemini 2.5 and Google Cloud Vision. A validation tab scores each model across structured sections and builds a PDF report, a history tab keeps every run, and a Detection Lab shows every detected word crop as a thumbnail with per image latency so I can visually verify the detection stage. All models are warmed before timing, every measurement is taken per stage, and a suite of roughly four hundred automated tests keeps the platform itself trustworthy. Its verdicts choose the OCR that powers the robot's reading games.

EventPlanners Digital Invitation SaaS ● LIVEFull Event Lifecycle SaaS · Live at eventplanners.app

A complete SaaS for event invitations, RSVPs and post event memories: a native Android app, dynamic web invitations, a Firebase backend, a Cloudflare CDN layer and Google Play Billing subscriptions. Independently designed, developed and deployed, and live at eventplanners.app.

What This Project Does

I built EventPlanners because I saw how much effort people put into organizing events, from weddings to birthday parties, and how scattered the tools were. I wanted one app that carries a host through the entire journey: designing the invitation, delivering it, tracking who is coming, running the event day, and thanking everyone afterward.

The Android app is built with Kotlin and Jetpack Compose following Material 3 design. Hosts design invitations with a template editor and more than 18 fonts, and an AI writer (OpenAI, proxied through Firebase Cloud Functions so no key ever ships in the app) drafts the wording for them. Delivery is built around WhatsApp: the app opens a personalized message for each guest one by one, runs a bulk send across the whole list, or copies a broadcast ready message, while tracking per guest delivery and RSVP status with sorting and filtering. Every event gets one shareable link that changes with the lifecycle: before the event it shows the invitation, after someone responds it shows their RSVP confirmation, and after the event it becomes the photo gallery.

The event day and everything after are covered too: QR code check in, a drag and drop seating chart, a budget tracker with PDF reports, schedules, vendors, guest surveys, a Live Wall photo slideshow and an analytics view. When the event completes, the thank you flow sends every accepted guest a personalized WhatsApp message with a photo from the event gallery attached, either the same photo for everyone or a random one per guest, with AI written templates, sent tracking and a resend option, so no guest is forgotten or thanked twice.

Behind the scenes, Firestore security rules enforce co host access, Cloud Functions send RSVP deadline reminders and push notifications, a home screen widget shows the event countdown with live RSVP counts, and a Cloudflare CDN with HMAC signed URLs serves every photo from the edge, cutting Firebase egress costs by over 95%. Subscriptions run through Google Play Billing across Free, Starter, Pro and Business tiers. I designed, developed and deployed every part of this myself. It is live at eventplanners.app.

End-to-end industrial vibration monitoring for two motors. Custom hardware (vibration sensors + power-switching PCB + battery backup) on Raspberry Pi, ML fault detection, and a full FastAPI + React dashboard with adaptive baselines and bearing-fault frequency analysis.

What This Project Does

At Hypen Holdings, I was tasked with building a system that could warn factory engineers before an industrial motor fails. Motor failures cause expensive unplanned downtime, and the traditional approach of scheduled maintenance either replaces parts too early (wasting money) or too late (after the damage is done). Predictive maintenance solves this by continuously monitoring the motor's health and catching the early signs of trouble.

I started with the hardware: I mounted three types of sensors on each motor (a tri-axial vibration sensor, a current sensor, and a temperature sensor) and connected them to a Raspberry Pi 4. I wrote Python code that samples these sensors at high speed, processes the data in real time, and packages it into compressed Parquet files that get uploaded to AWS S3 every minute. Because factory power can cut out at any time, I designed a custom PCB with a battery backup and high-speed power switching circuit, so the Pi keeps running and no data is lost during an outage.

On the cloud side, a FastAPI server running on DigitalOcean pulls the Parquet files from S3 every five minutes, runs analytics (FFT spectrum analysis, bearing fault frequency detection, ISO 10816 vibration severity classification), and stores hourly summaries in a PostgreSQL database. The system learns what "normal" vibration looks like for each specific motor during a baseline period, then flags any deviation using a statistical threshold approach. The React web dashboard shows everything in real time: FFT plots, trend charts, bearing health indicators, and a maintenance log with a timeline view. I deployed the whole stack using Docker Compose behind Nginx.

PROJ. 072023 Midas Safety (Pvt) Ltd · Awissawella, Sri Lanka

Heat Transfer Machine — Glove Printing AutomationProduction-Deployed Industrial PLC System

Production-deployed automation for printing on industrial gloves. Delta PLC with recipe-driven sequencing, HMI touchscreen, and pneumatics integration. Replaced a manual process on the Awissawella production floor.

What This Project Does

At the Midas Safety glove factory in Awissawella, designs are printed onto industrial gloves by pressing them against a heated plate at a specific temperature for a specific duration. Before I built this system, an operator did everything manually: setting the temperature, watching a timer, pressing and releasing the pneumatic cylinders by feel. The problem was inconsistency. Some prints came out too light, others were scorched, and the defect rate was higher than it needed to be.

I designed and built an automated version using a Delta PLC (Programmable Logic Controller). The core idea is recipe-based operation: an engineer defines a recipe for each glove type (specifying the exact temperature, dwell time, and pressure), and the operator simply selects the recipe on the HMI touchscreen and presses start. From there, the PLC handles everything automatically. It heats the plate to the precise setpoint using PID control (holding within half a degree), sequences the pneumatic cylinders for exactly the right press duration, then releases and advances to the next position.

I also designed the electrical control panel, wired all the I/O modules, programmed the safety interlocks (the machine will not operate if the door is open or the temperature exceeds safe limits), and built an alarm management system that logs faults. The result was a measurable reduction in glove defect rate because the machine now delivers the exact same temperature and timing on every single cycle, regardless of which operator is running it. This machine has been running on the production floor since 2023.

  • HMI touchscreen UI: recipe selection, run/stop, temperature setpoint, process monitoring, alarm display and acknowledgment.
  • Pneumatic integration: solenoid valve sequencing for press/release cycles, 6 bar supply, timed coordination with heater plate.

PROJ. 082023 University of Peradeniya
EmbeddedIoTPCB Design

Smart Home Automation System (ESP32)Custom PCB + Voice Assistants + Touchscreen

Custom smart-home controller built around ESP32. PCB designed in KiCad, firmware in ESP-IDF, integrated with Google Home and Alexa, with touchscreen for local control. Works offline via local fallback.

What This Project Does

For my university project, I decided to build a smart home controller entirely from scratch rather than using an off-the-shelf solution like a Raspberry Pi with Home Assistant. I wanted to understand every layer: the circuit board, the firmware, the communication protocols, and the cloud integrations.

I designed a custom PCB in KiCad centered around an ESP32 microcontroller. The board includes relay drivers for switching lights and appliances, inputs for a DHT temperature and humidity sensor, a PIR motion detector, and a light-dependent resistor. There is also a capacitive touchscreen connected for local control, so you can tap through different room presets ("Movie Mode" dims the lights and turns off the ceiling fan, "Sleep Mode" turns everything off except a night light) without needing your phone or voice assistant.

The firmware is written in C using Espressif's ESP-IDF framework. It runs a scene engine for preset configurations, a schedule manager for time-based automation (like turning on porch lights at sunset), and an OTA updater so I can push firmware changes over WiFi without physically accessing the device. The system connects to Google Home and Amazon Alexa through MQTT for voice control. The key design decision was making it local-first: all the automation logic runs on the ESP32 itself. If the internet goes down, the touchscreen and scheduled automations keep working normally. The cloud services are nice additions, not requirements.
